## 0. 한 줄 요약

**관객은 휴대폰 번호를 넣고, 신분증과 얼굴로 본인인증하고, Face ID를 등록하면 끝. 입구에서 "입장하기"를 누르고 Face ID 한 번, 60초 안에 스태프 단말기에 폰을 대면 스태프 화면이 초록색으로 바뀐다.** 그 초록은 우리 서버가 아니라 Monad 체인이 확정한 결과다. 관객은 지갑도 가스비도 코인이라는 단어도 보지 않고, 입장 순간 인터넷조차 필요 없다. 가스는 전부 우리가 낸다.

한 문장 피치(영문, 제출용):
> Face ID arms your ticket. A tap hands the gate a signature that never leaves your phone's secure chip. The gate, acting on the organizer's on-chain authority, writes the check-in to Monad, and the chain, not our server, decides. Nothing on the attendee's screen is worth screenshotting, and nothing on our server is worth hacking.

## 2. 왜 이 제품인가

블록체인 티켓팅이 전멸한 이유는 셋이었다. 체인이 검표 경로에서 너무 느리거나 불안정했다, 암표의 실제 해법은 NFT가 아니라 신원 결속이었다, 소비자가 체감할 개선점이 없었다.

MONTI의 답:

1. **체인이 검표 경로 안에 있어도 되는 체인을 골랐다.** Monad는 0.3초 블록, 약 0.6초 확정이다. 게이트 단말기가 보낸 체크인이 이벤트로 보이기까지 중간값 0.7초, 최악 3초. 그래서 **체인이 판정**한다. 서버가 뚫려도 가짜 입장이 생기지 않는다.
2. **암표는 신원으로 막는다.** 티켓은 신분증과 얼굴로 확인된 한 사람의 계정에만 들어가고, 입장은 그 사람의 Face ID와 그 사람의 폰 보안 칩으로만 된다. 양도는 회원끼리만, 주최자가 정한 규칙 안에서만.
3. **소비자가 체감하는 것.** 캡처할 것도 보여줄 것도 없다. 인터넷이 안 터지는 공연장에서도 폰을 대면 끝. 폰을 잃어도 본인인증만 다시 하면 티켓이 돌아온다.

## 3. 제품 원칙

1. **체인이 데이터베이스다.** 공연, 티켓, 게이트, 역할과 권한(allowlist), 양도, 수동 승인, 기기 등록, 메타데이터 해시는 전부 Monad에 쓴다. 체인 밖에 두는 것은 법적으로 올리면 안 되는 개인정보(이름, 전화번호, 신분증, 얼굴 사진)와 속도용 캐시뿐. 체인에 없는 관리자, 게이트, 매니저는 존재하지 않는 것이다.
2. **크립토 단어 금지.** 지갑, NFT, 민팅, 가스, 체인, 토큰, 트랜잭션은 관객 화면 어디에도 없다. "티켓", "입장", "양도", "공개 기록"만.
3. **관객 폰은 서명만 만든다. 변경은 권한 있는 쪽이 체인에 쓴다. 가스는 우리가 낸다.** 서버는 대신 서명하지 않는다. 서버에는 관객 키도 발행 권한 키도 없다.
4. **판정은 스태프 화면에, 근거는 체인에.** 관객 폰의 초록은 참고용.
5. **관객 폰에는 훔칠 것이 없다.** 나가는 것은 특정 게이트, 특정 순간에만 유효한 서명 하나뿐이다.
6. **신원이 복구 수단.** 폰 분실, 패스키 유실은 본인인증 재수행 또는 문자 인증으로 복구한다. 시드 구문은 없다.
7. **코드는 웹 하나.** 관객, 주최자, 스태프 화면 전부 웹 코드베이스. 네이티브는 NFC, 패스키 브리지, 기기 키, HCE 네 곳에만 얇게.

## 4. 용어 (비개발자용)

| 용어 | 뜻 |
|---|---|
| 패스키 | Face ID나 지문으로 로그인하는 표준. 비밀키는 폰 보안 칩 안에만 있고 절대 밖으로 안 나온다. iCloud·Google로 다른 폰에 동기화된다. **계정의 주인 열쇠** |
| 기기 키 | 앱이 이 폰의 보안 칩 안에 따로 만드는 열쇠. 동기화되지 않는다. Face ID 뒤 60초 동안만 쓸 수 있게 칩이 강제한다. **입장에 쓰는 열쇠** |
| P-256 | 두 열쇠가 쓰는 서명 방식. Monad에는 이 서명을 6,900 gas(약 0.02원)에 검증하는 내장 기능이 있다(프리컴파일 0x0100) |
| 스마트 계정 | "이 열쇠의 서명이 맞으면 실행해라"라는 규칙이 코드로 적힌 계정. 관객, 게이트 단말기, 관리자 모두 이것을 쓴다 |
| 트랜잭션 요청(유저옵) | "이걸 실행해 주세요" 묶음. 번들러가 받아 체인에 넣는다 |
| 번들러 | 요청을 모아 체인에 넣는 우체부. 아무나 운영할 수 있어 종속이 없다 |
| 페이마스터 | 가스를 대신 내주는 컨트랙트. 우리 예산으로 낸다 |
| 게이트 1회용 번호 | 게이트 단말기가 3초마다 새로 만드는 1회용 번호. 은행 OTP와 같은 원리인데 만드는 쪽이 단말기다 |
| 무장(arm) | "입장하기" 버튼과 Face ID로 기기 키를 60초 동안 서명 가능 상태로 만드는 것 |
| NFC | 폰을 갖다 대면 통하는 근거리 통신. 우리 방식에서는 폰이 **읽고 쓰기** 둘 다 한다 |
| HCE | 폰이 "카드인 척"하는 기능. 안드로이드는 자유, 아이폰은 애플 허가제이고 **한국은 허가 대상이 아님**. 그래서 단말기는 안드로이드 |
| Web NFC | 웹 브라우저에서 NFC를 읽고 쓰는 기능. **안드로이드 Chrome에만 있고 아이폰에는 없다** |
| 껍데기(Capacitor) | 웹앱을 그대로 감싸서 앱스토어에 올릴 수 있게 하고, 필요한 네이티브 기능만 플러그인으로 붙이는 도구 |
| allowlist | 체인에 적힌 "이 계정은 이 권한이 있다" 목록 |
| 확인 서명 키(어테스터) | "이 사람은 본인인증을 통과했다"를 체인에 증명하는 우리 쪽 서명 키. 앱 서버가 아니라 별도 금고(HSM)에 둔다 |
| CID | 파일의 내용 지문. 체인에 적어두면 파일이 바뀌었는지 누구나 확인 가능 |
| 인덱서 | 체인 기록을 읽기 쉽게 정리하는 서버. 목록과 영수증 페이지용. 권한 판정에는 쓰지 않는다 |

## 5. 사용자 여정

### 5.1 관객: 가입 (한 번만)

1. 앱 설치(또는 웹 접속) → **휴대폰 번호** → 문자 인증번호. 이메일은 없다. 안드로이드는 Google이 문자를 자동으로 확인해 번호 입력이 생략되는 경우가 많다. 전화번호 하나에 계정 하나다.
2. **Face ID 등록**("Face ID로 잠금 설정"). 이것이 패스키다. 폰 뒤에서 스마트 계정 주소가 만들어지고, 첫 트랜잭션으로 계정이 배포되며 신원이 **등급 0**으로 체인에 등록된다. 가스는 우리가. 여기까지 1분.
3. 앱은 이 폰의 보안 칩에 **기기 키**를 만들어 활성 기기로 체인에 등록한다.
4. **본인인증(선택, 필요할 때)**: "KYC 필요" 행사의 티켓을 받으려 하면 "이 행사는 본인인증이 필요해요" 안내 → 신분증 촬영 + 얼굴 촬영(30초, Didit, 시스템 브라우저) → 통과하면 계정이 **등급 1**로 올라간다. 같은 얼굴이 이미 다른 계정에 있으면 거절된다(1인 1계정). 프로필에서 미리 해둘 수도 있다.

이후 로그인은 **패스키만**이다.

| 계정 등급 | 조건 | 할 수 있는 것 |
|---|---|---|
| 0 | 전화번호 + Face ID | 일반 행사 티켓 받기·양도·입장, 대화방 |
| 1 | 0 + 신분증·얼굴 확인 | 위 전부 + **KYC 필요 행사** 티켓 받기·양도받기·입장(게이트에서 사진 대조) |

### 5.2 관객: 티켓 받기

1. 공연이나 모임 선택. 카드와 상세에 **"KYC 필요"** 배지가 있으면 본인인증(등급 1)이 있어야 받을 수 있다.
2. "참가 신청" 또는 "티켓 받기" → (KYC 필요 행사인데 등급 0이면 본인인증 안내로 이동) → Face ID → 폰이 "받기" 요청을 체인에 보낸다(가스는 우리가). 컨트랙트도 등급을 검사하므로 앱을 우회해도 못 받는다. 티켓이 "내 티켓"에 뜬다. 상태 **입장 전**. 바코드는 없다.
3. 유료 티켓은 해커톤 MVP 밖이다. 설계는 8.7에 있다: 카드(Eximbay) 또는 USDC 결제 완료 → 확인 서명 키가 결제 확인 서명(voucher) 발급 → 관객이 voucher와 함께 "받기". 유료 티켓 판매는 **웹에서만**, iOS 앱은 보기·입장 전용.

### 5.3 관객: 입장 (공연 당일)

1. 입구에서 **"입장하기"** → **Face ID**. 기기 키가 60초 동안 무장된다. 화면에 "60초 안에 단말기에 대세요" 카운트다운. 코드도 바코드도 없다.
2. 폰을 스태프 단말기에 댄다(아이폰은 시스템 NFC 시트). 폰이 게이트 1회용 번호를 읽고, 그 게이트가 체인에 등록된 진짜 게이트인지 확인하고, 기기 키로 서명해서 **같은 탭 안에서 단말기에 써서 돌려준다.** 진동 한 번. 폰의 역할은 끝. 인터넷이 필요 없다.
3. 단말기가 그 서명을 들고 **주최자의 게이트 권한**으로 체인에 체크인 트랜잭션을 보낸다.
4. 0.7초쯤 뒤 **스태프 화면 초록 + 본인인증 사진**. 스태프가 얼굴을 본다. 통과.
5. 잠시 뒤 관객 폰에 푸시 "입장 완료". 티켓 이미지가 "입장 완료"로 바뀐다(체인이 바꾼 것).
6. 같은 폰을 다시 대면 스태프 화면 빨강 "이미 입장 12:03 · Gate A".

NFC가 안 되는 상황(기기, 브라우저에서 접속한 경우)이면 폰이 같은 내용을 QR로 띄우고 스태프가 찍는다. 이후는 동일하다.

### 5.4 관객: 양도 (3경로 + 미가입자 초대)

받는 사람을 찾는 길은 셋이다. **닉네임**, **가입된 EVM 주소**, **전화번호(국가 코드 + 번호)**.

1. 티켓에서 "양도" → 세 탭 중 하나로 상대를 찾는다. 앱이 상대가 회원인지 확인한다(닉네임은 체인 조회, 주소는 회원 여부 조회, 전화번호는 서버의 암호화 색인 조회).
2. **회원이면**: 앱이 먼저 검사한다(이 공연 티켓 최대 보유 수, 양도 마감, 입장 전, 양도 횟수). 하나라도 걸리면 알람을 띄우고 보내지 않는다. 통과하면 Face ID → 양도 트랜잭션. 컨트랙트가 같은 규칙을 다시 검사한다.
3. **전화번호 상대가 미가입이면**: Face ID → 체인에 "이 번호의 사람에게 전달 예약"(offer)을 걸고, **보내는 사람의 폰 문자 앱이 열려** 초대 문자를 보낸다(문자 발송 비용 0, 스팸 위험 0). 받는 사람이 앱을 설치하고 가입(전화 인증 + 본인인증 + Face ID)을 마치면 예약된 티켓이 **자동으로 전달**된다. 보낸 사람은 전달 전까지 취소할 수 있고, 예약은 만료 시간이 있다.
4. 받은 티켓은 "내 티켓 → 받은 티켓"에 뜬다. 예약 중인 티켓은 보낸 사람 쪽에서 "양도 대기"로 표시된다.

전달 예약(offer)도 컨트랙트가 관리한다. 받는 사람의 계정이 확정될 때 우리 확인 서명 키가 "이 번호 = 이 계정"을 증명하고, 컨트랙트가 그 증명을 검사한 뒤 일반 양도와 같은 규칙으로 옮긴다. 보낸 사람이 그 사이 입장하거나 다른 곳에 양도하면 예약은 자동 무효다.

### 5.4a 관객: 행사 대화방

같은 행사의 티켓을 가진 사람들끼리만 들어갈 수 있는 대화방이 행사마다 하나씩 있다. 하단 탭 "대화"를 누르면 내가 속한 대화방이 모두 나오고, **순서는 드래그로 내 마음대로** 바꿀 수 있다. 행사가 끝나는 시각이 지나면 대화방이 닫히고 읽기도 쓰기도 안 된다. 닫힌 방은 하루 뒤 목록에서 사라진다. 티켓을 양도하면 방에서 나가진다. 주최자는 공지를 고정할 수 있다. 신고 버튼이 있다.

대화 내용은 체인에 올리지 않는다(원칙 1의 명시적 예외: 일시적 사용자 콘텐츠). Firebase 실시간 DB에 두고, 입장 자격은 체인의 티켓 보유를 서버가 확인해 부여한다.

### 5.5 관객: 폰 분실·교체

| 상황 | 흐름 |
|---|---|
| 잃어버림, 해킹 의심 | 다른 폰이나 웹에서 "내 기기 잠금". 즉시. 잠긴 동안 입장 불가 |
| 새 폰, 패스키가 동기화됨 | 새 폰에서 Face ID → "새 기기입니다" → 문자 인증 또는 본인인증 재수행 → **마지막 기기 등록 후 7일이 지났으면** 즉시 활성화, 아니면 7일 뒤 |

| 공연이 7일 안인데 잠겨 있음 | 현장에서 매니저가 사진 대조 후 수동 승인. 승인자와 사유가 체인에 남는다 |

| 내 티켓 | 탭: **사용 전 / 사용 후**. 상태 배지: 입장 전·입장 완료·양도 대기·양도됨·취소됨. **받은 티켓** 인박스 | 보강 |
| 티켓 상세 | 행사 정보, 상태, 좌석·종류, 캘린더 추가, 길찾기, **양도**, 플로팅 "입장하기" | 보강 |
| 입장 모드 | 입장하기 → Face ID → 60초 카운트다운 → 탭 → 결과. NFC 불가 시 QR | 있음 |
| 양도 | 닉네임 / 주소 / 전화번호. 미가입자 문자 초대 | 추가 |
| 대화 | 행사별 대화방, 순서 변경, 종료 시 닫힘 | 추가 |
| 알림 | 입장 완료, 티켓 받음, 양도 완료, 행사 공지, 대화 | 보강 |
| 프로필 | 닉네임 설정, 언어, 기기 잠금, 새 기기 등록 상태, 공개 기록, 계정 삭제 요청, 도움말 | 추가 |
| 주최자 전환 | "주최자 되기" | 추가 |

빠져 있던 것 중 중요한 순서: **행사 상태(초안·게시·취소)**, **닉네임과 프로필**, **알림 센터**, **영어 UI**, **받은 티켓 인박스**, **탐색 필터**. 전부 v2.4에 넣었다.

### 5.7 현장 스태프 (안드로이드 단말기)

1. 스태프 앱 실행 → 관리자가 준 게이트 QR 스캔 → 단말기 보안 칩에 게이트 키 생성 → 게이트 계정 주소가 관리자 화면에 뜨고 관리자가 승인하면 **체인 allowlist에 등록** → PIN 설정.
2. "TAP HERE". 단말기는 3초마다 새 1회용 번호를 NFC로 내보낸다. 이 화면에서는 단말기가 NFC를 **읽지 않는다**(읽기 모드를 켜면 아이폰과 충돌한다).
3. 관객이 대면 단말기가 서명을 받아 체인에 보내고, **체인 이벤트를 받아** 초록(사진) 또는 빨강(사유).
4. 인터넷이 끊기면 "OFFLINE". 스냅샷으로 로컬 검증하고 트랜잭션을 큐에 쌓아 복구 후 보낸다. 관객은 영향 없다.
5. 예외는 PIN + 사유 코드로 수동 승인(권한 있으면) 또는 결재 요청(없으면).

## 6. 핵심 결정 1: "Face ID로 무장 → 탭 → 게이트가 체인에 쓴다"

### 6.1 세 가지 후보

| 후보 | 흐름 | 판정 |
|---|---|---|
| A. 폰이 신호를 낸다 | 폰이 NFC로 "나 미사용 티켓" 신호 → 단말기가 읽음 | **탈락.** 아이폰은 신호를 못 낸다(HCE 허가제, 한국 제외). 폰이 자기 상태를 주장하는 구조는 앱 변조로 뚫린다. 고정 신호는 복제된다 |
| B1. 폰이 읽고 폰이 체인에 보낸다 | 폰이 1회용 번호를 읽고 서명해 **폰이** 체인에 전송 | 가능하지만 **관객 폰에 인터넷 필요.** 만석 공연장은 LTE가 안 터진다 |
| **B2. 폰이 읽고 쓰고, 게이트가 체인에 보낸다** | Face ID로 무장 → 탭 → 폰이 1회용 번호를 읽고 기기 키로 서명해 **NFC로 돌려줌** → **게이트 단말기가 주최자 권한으로** 체인에 전송 | **채택.** 관객 인터넷 불필요. 단말기 하나만 연결되면 된다. 오프라인 큐잉이 자연스럽다 |

B2는 창업자 제안("Face ID로 NFT를 변조 가능 상태로, 태그하면 우리 권한으로 변조 트랜잭션")의 구현이다. "변조 가능 상태(무장)"는 체인이 아니라 **폰 보안 칩 안**에 둔다. 체인에 올리면 관객 인터넷이 다시 필요해지고 1원이 들며 보안상 얻는 게 없다. NFT가 눈에 보이게 바뀌는 순간은 체크인 트랜잭션이다: 입장 전 → 입장 완료.

같은 흐름(안드로이드 HCE 쓰기 가능 태그 ↔ 아이폰 Core NFC 읽기 + 쓰기)이 오픈소스 지갑 두 곳(Zeus, Cashu)에서 실제로 돌아가고 있다.

### 6.2 "상태에 따라 신호가 다르다"는 원래 의도

살아 있다. 상태를 보여주는 주체가 폰이 아니라 단말기와 체인이다. 첫 탭은 초록, 두 번째 탭은 빨강 "이미 입장".

### 6.3 위협 모델 (쉬운 말)

| # | 공격 | 결과 |
|---|---|---|
| T1 | 화면 캡처, 영상 | 무의미. 관객 화면에 크리덴셜이 없다 |
| T2 | 태그 복제 | 차단. 단말기가 예측 불가능한 1회용 번호를 요구하고, 폰은 그 번호에 대한 서명만 돌려준다 |
| T3 | 앱 변조로 "미사용" 주장 | 차단. 폰은 상태를 주장하지 않는다. 체인이 결정한다 |
| T4 | **공범 릴레이**: 티켓 있는 A는 집에, 티켓 없는 B가 게이트에. B 폰이 1회용 번호를 A에게 보내고 A가 무장된 폰으로 서명해 돌려주면 B가 단말기에 쓴다. 체인은 "A 입장". 들어간 사람은 B | **잔존.** 티켓은 한 번만 쓰이므로 이중 입장은 아니다. "본인이 들어왔다"만 깨진다. NFC는 거리를 증명 못 하므로 스태프의 사진 대조가 통제 수단. 양도가 공식 허용되므로 친구에게 줄 사람은 양도하면 되고, 릴레이는 KYC를 못 받는 사람을 들이는 용도로만 남는다 |
| T5 | 입장 후 폰을 친구에게 넘김 | 실익 없음. 티켓은 최종 상태 |
| T6 | 패스키가 두 번째 폰에 동기화 | **하드웨어로 차단.** 입장 서명은 동기화되지 않는 기기 키만 만들 수 있고, 활성 기기 1대가 체인에 등록돼 있다 |
| T7 | 폰 도난 | 차단. 무장에 Face ID 필수, 무장은 60초. 기기 잠금 즉시 가능 |
| T8 | 스태프 결탁 | 잔존. 수동 승인은 승인자 주소, 역할, 사유가 체인에 남는다 |
| T9 | 공연장 인터넷 다운 | 관객은 원래 무관. 단말기는 스냅샷 로컬 검증 + 큐잉(12장) |
| T10 | 체인 RPC·번들러 지연 | 단말기 쪽만 영향. RPC·번들러 다중화 + 큐잉 |
| T11 | 백엔드 침해 | **부분 차단.** 서버에 관객 키도, 게이트 키도, 티켓 발행 권한도 없다. 단말기는 체인만 믿는다. 다만 **확인 서명 키(어테스터)가 털리면** 신원 등록·KYC 등급·계정 교체를 위조할 수 있다. 계정 교체는 `AccountRotated`로 체인에 남고, **티켓은 24시간(`MIGRATE_DELAY`) 동안 따라가지 않으며**, 그 24시간 안에 **직전 계정 본인이** `cancelRotation()`으로 되돌릴 수 있다(되돌려도 7일 쿨타임은 되감기지 않아 공격자는 다음 시도까지 꼬박 기다린다). 24시간 안에 되돌리지 않으면 미사용 티켓이 넘어간다. 남는 피해: KYC 등급 위조, 임의 신원 등록, 계정 잠금(현장 대량 DENY), 서비스 중단, 개인정보 유출(암호화로 대응). **어테스터 키를 Cloud KMS로 옮기는 것이 근본 해결이고 정식 출시 전 필수다(10.3).** 못 하는 것: 티켓 발행, 티켓 취소, 입장 처리, 행사 생성, 이미 입장했거나 취소된 티켓 이동. 되돌리기 자체의 잔존(**MVP가 받아들인 위험**): 도난·동기화된 **옛** 패스키가 정당한 교체 한 번을 그 24시간 안에 무효화해 복구를 다음 쿨타임으로 미룰 수 있고, 이것은 반복될 수 있다. 되돌리기에도 옛 폰의 생체 인증이 필요하므로 그 폰이 없는 절도범은 못 한다. 신원을 빼앗지는 못한다 — 되돌려도 교체가 건 기기 잠금이 남아 되살아난 계정은 문에서도 양도에서도 막히고, 그걸 푸는 `setActiveDevice`는 T6이 이미 받아들인 잔존 권한이다 |
| T12 | 더블 탭, 재시도 | 컨트랙트가 두 번째를 거부. 단말기는 첫 판정 유지 |
| T13 | 두 게이트에서 같은 티켓을 같은 초에 | 체인이 원자적으로 하나만 성공 |
| T14 | **가짜 게이트**: 사기꾼이 공연장 밖에 폰을 놓고 "여기서 티켓 미리 확인하세요" | **이중 차단.** ① 관객 폰이 서명을 쓰기 전에 그 게이트가 체인 allowlist에 있는지 확인한다. ② 설령 서명을 얻어도 사기꾼 계정은 allowlist에 없어 체크인 트랜잭션이 거부된다. 진짜 단말기를 도난당해도 관리자가 allowlist에서 빼면 끝이다. v2.6부터 그 폐기(`revokeGate`)는 **가스 없이** 되고, 폐기된 게이트 계정은 페이마스터의 스폰서 대상에서도 즉시 빠지며, 그 주소를 새 단말기로 **다시 등록할 수 있다**. 폐기된 게이트는 오프라인 큐(`checkInLate`)도 흘리지 못한다 |
| T15 | 단말기 도난 후 오프라인 큐 조작 | 큐의 트랜잭션은 관객 기기 키 서명이 있어야만 체인이 받는다. 단말기 혼자서는 못 만든다 |

## 7. 입장 절차 (단계별)

**불변 원칙**: 관객 폰은 서명만 만든다. 단말기는 1회용 번호를 주고 서명을 받아 체인에 쓴다. 체인이 판정한다. 스태프 화면이 보여준다. 서버는 힌트만 준다.

### 7.1 사전 준비

1. 가입 시 관객의 패스키 공개키로 스마트 계정이 배포되고, 기기 키가 활성 기기로 체인에 등록된다.
2. 티켓은 관객 계정이 "받기" 트랜잭션으로 받는다.
3. 스태프 단말기의 게이트 키(P-256, 안드로이드 보안 칩)로 **게이트 계정**(스마트 계정)이 만들어지고, 관리자가 그 계정을 공연의 게이트 allowlist에 등록한다. 공연 시간에 관리자가 게이트를 "연다".

### 7.2 입장 순간

| 단계 | 주체 | 동작 |
|---|---|---|
| 1 | 관객 | **"입장하기" → Face ID.** 기기 키가 60초 동안 무장된다. 화면: 카운트다운 |
| 2 | 단말기 | HCE로 NFC 태그(Type 4, 쓰기 가능)를 흉내 내며 3초마다 **게이트 1회용 번호** G를 내보낸다. `G = {gate_id, event_id, issued_at, nonce} ‖ sig_gate(G)`. 이때 단말기는 NFC 읽기 모드를 켜지 않는다 |
| 3 | 관객 폰 | 탭 → G를 읽는다 → `sig_gate`를 체인 allowlist의 게이트 키(앱이 캐시, 이벤트로 갱신)로 검증. 가짜 게이트면 여기서 멈추고 "등록되지 않은 단말기" 표시 |
| 4 | 관객 폰 | 기기 키로 서명 `S = sign_device(sha256(abi.encode(chainId, Ticket 주소, tokenId, gate_id, event_id, nonce, issued_at)))`. **일곱 낱말(224바이트)이고 앞의 두 낱말이 v2.6에서 새로 붙었다** — 체인과 배포본을 묶어, 테스트넷 서명이 메인넷에서, 옛 배포본의 서명이 새 배포본에서 통하지 않는다. 같은 값을 컨트랙트의 `deviceDigest(...)` 조회로 확인할 수 있다(클라이언트는 그걸 기준으로 한 벡터를 고정한다). 서명은 **low-`s`만** 받는다 — `s > N/2`이면 `s = N − s`로 정규화해서 보낸다. Face ID 재요구 없음. **같은 탭 안에서 NFC 쓰기로 `{tokenId, S}`를 단말기에 돌려준다.** 진동. 폰 역할 끝. **인터넷 불필요** |
| 5 | 단말기 | `checkIn(tokenId, G, S)` 트랜잭션 요청을 **게이트 계정으로** 번들러에 보낸다(Pimlico, 예비 Alchemy). 가스는 페이마스터. 전송 전 캐시된 스냅샷으로 사전 검증해 실패 트랜잭션을 줄인다. 인터넷이 끊긴 상태였다면 같은 값을 큐에 쌓아 두었다가 복구 후 `checkInLate(tokenId, G, S)`로 보낸다(12장) |
| 6 | 체인(컨트랙트) | ① msg.sender가 이 공연의 등록된 게이트이고 열려 있는가 ② `S`가 `ownerOf(tokenId)`의 활성 기기 키 서명인가(P-256 프리컴파일) ③ `S` 안의 gate_id가 msg.sender의 게이트인가 ④ 현장 경로는 `now - issued_at ≤ 60초`. 복구 후 기록 경로(`checkInLate`)는 개장 −12시간 ~ 폐장 +12시간 ⑤ 티켓이 이 공연 것이고 입장 전이며 취소되지 않았고 계정이 잠기지 않았는가. **v2.6부터 보유자가 지금도 `Identity` 멤버인지도 다시 본다** — 계정 교체로 밀려난 옛 계정이 티켓을 들고 있으면 `NotMember`로 되돌아온다(13장에서 `TX_FAILED`). 하나라도 실패하면 되돌린다 |
| 7 | 체인 | 통과하면 체크인 기록 + `CheckedIn(tokenId, eventId, gateId, nonceHash, ts)` 이벤트. `tokenURI`가 "입장 완료"로 바뀐다 |
| 8 | 단말기 | 자기 요청의 결과와 `monadLogs` 구독으로 이벤트를 받아 **초록 + 사진**. 추측 실행 단계에서 켜고(0.7초), 확정되면 굳힌다(+0.6초) |
| 9 | 서버 | 같은 이벤트를 Tenderly 알림으로 받아 인덱서 갱신, 관객 폰에 "입장 완료" 푸시. 판정 근거가 아니다 |

### 7.3 파라미터

| 항목 | 값 | 이유 |
|---|---|---|
| 무장 시간 | 60초 | 줄 서서 Face ID 누르고 대기까지. 지나면 다시 누르면 된다 |
| 1회용 번호 회전 | 3초 | 싸고, 오래된 번호 창을 줄인다 |
| 번호 유효기간(체인 검사) | 60초 | 탭 → 전송 → 블록 포함까지 여유 |
| 큐 유효기간(체인 검사) | 개장 −12시간 ~ 폐장 +12시간 | 오프라인 큐 전용(`checkInLate`). 현장 60초 창과 무관하며, 하한이 게이트의 서명 사전 수확을 막는다 |
| 단말기 시계 | NTP 동기화 | 컨트랙트가 `block.timestamp`로 검사 |
| 단말기 화면 | 2초까지 "확인 중", 5초 넘으면 "다시 대세요" | **시간 초과로 소프트 승인 금지** |
| 탭 실패 재시도 | 아이폰 "세션 만료" 시 즉시 재탭 안내 | 단말기 간섭(18장) |
| NFC 쓰기 페이로드(관객 → 단말기) | CBOR **162바이트**, `monti.app:s` NDEF 짧은 레코드로 **176바이트**(헤더 3 + 타입 이름 11 + 페이로드 162), 레코드 1개 | Type 4 CC 한도 안. `deviceSig`가 바이트가 아니라 130자 16진수 **문자열**이라 순수 바이트 합(32 + 64 + 부가)보다 크다 |
| NFC 읽기 페이로드(단말기 → 관객) | `monti.app:g` 게이트 코드 레코드. 위보다 **짧다**(서명 하나와 네 필드뿐) | 3초마다 교체되므로 작을수록 좋다 |
| 예상 지연 | 중간값 0.7초(추측) / 1.3초(확정), 최악 3.0 / 3.6초 | 조사 실측 |

### 7.4 왜 체인이 판정해도 되는가

Monad는 확정이 0.6초이고 추측 실행 상태를 RPC가 바로 노출한다. 두 게이트 동시 탭은 컨트랙트가 원자적으로 처리하므로 DB 락이 필요 없다. 관객 폰은 체인과 통신하지 않으므로 관객 쪽 네트워크 문제는 사라졌다. 남는 의존은 단말기 하나이고, 그건 스냅샷과 큐잉으로 버틴다. 창업자의 결정: **서버보다 체인을 믿는다.**

### 8.2 계정 = 순수 패스키 스마트 계정 (벤더 없음, Mera 없음)

| 열쇠 | 어디에 | 언제 쓰나 | 동기화 |
|---|---|---|---|
| **패스키** | 폰 보안 칩(iCloud·Google 동기화) | 로그인, 티켓 받기, 양도, 기기 등록, 계정 소유 | 된다 |

계정은 ERC-4337 스마트 계정, 소유자 = 패스키 공개키. `Identity`가 계정 ↔ 활성 기기 키를 잇는다.

| 후보 | 결정 |
|---|---|
| Coinbase Smart Wallet 컨트랙트 + viem `toCoinbaseSmartAccount` | **1순위.** MIT. 패스키 소유자를 viem이 공식 지원. P-256 프리컴파일 자동 감지. 메인넷 배포됨, 테스트넷은 CREATE2로 같은 주소 재배포. **관객·게이트·관리자 계정 모두 같은 컨트랙트** |

| Privy, Dynamic, Turnkey | 제외. 벤더 없이 |

### 8.4 페이마스터 (우리 부담 기본, 프로젝트 예산으로 확장)

- 페이마스터 컨트랙트 1개. 예산 칸: `budget[PLATFORM]`, `budget[projectId]`.
- 프로젝트 생성 시 `sponsor = PLATFORM`. 나중에 주최자가 "내 가스 지갑 만들기"를 누르면 빈 예산 칸이 열리고 충전하면 `sponsor = SELF`. UI는 MVP 밖, 컨트랙트 구조는 MVP 안.
- 후원 대상: 관객 계정(받기, 양도, 기기 등록), 게이트 계정(체크인, 수동 승인), 관리자 계정(프로젝트 생성, allowlist 변경). 대상 컨트랙트와 함수 허용 목록으로 제한.
- **검증 단계에서 `maxCost`를 예약하고 `postOp`에서 실제 비용으로 정산한다.** 검증이 `budget[slot] >= maxCost`를 확인하고 `abi.encode(slot, maxCost)`를 넘기면 `postOp`이 `actualGasCost`만큼 깎는다. `postOp` 없이 검증에서 바로 차감하면, `maxFeePerGas`를 부풀린 유저옵 한 건이 예산 칸을 0으로 만드는 동안 EntryPoint는 차액을 예치금으로 돌려줘 돈이 갇힌다.
- 프로젝트별 예산을 읽으려면 페이마스터 **스테이킹** 필요(번들러 정책: 약 $1,000 상당, 해제 대기 1일).
- **티켓 컨트랙트는 누가 가스를 내는지 모른다.** 다른 페이마스터든 자기 MON이든 동작한다.

### 10.2 컨트랙트 (4개)

**`Identity`**
- `personId`는 **아무 의미 없는 난수 32바이트**다. 해시가 아니다. 난수 ↔ 실제 사람의 연결은 Firestore에만 있고, 체인만 봐서는 누구인지 알 수 없다
- `register(personId, account, deviceKey)` 확인 서명 키만
- `rotateAccount(personId, newAccount)` 확인 서명 키만, 7일 쿨타임. 옛 계정의 기기를 잠그고, 직전 계정을 24시간 되돌리기용으로 기록한다
- `setActiveDevice(deviceKey)` 계정 본인, 7일 쿨타임 · `lockDevice()` 계정 본인 또는 확인 서명 키
- 조회: `accountOf`, `isMember`, `activeDevice`, `locked`
- 이벤트 `Registered`, `AccountRotated`, `DeviceChanged`, `DeviceLocked`

**`Organizers`** (allowlist)
- `createOrganizer(owner)`, `setAdmin(orgId, admin, permissionBits)`, `setManager(orgId, manager, canApprove)`, `transferOwner`
- `registerGate(orgId, eventId, gateAccount, gateKey)`, `revokeGate`, `openGate`, `closeGate`
- 조회: `hasPermission`, `isOpenGate(eventId, account)`, `gateKey`
- 이벤트 `AdminSet`, `ManagerSet`, `GateRegistered`, `GateRevoked`, `GateOpened`, `GateClosed`

**`Ticket`** (ERC-721)
- `createEvent(orgId, meta)` 관리자. `meta` = 제목 해시, 소개글 해시, 이미지 CID, 시작·종료, 장소 해시, 종류별 {가격, 수량, 1인 최대}, 신청 기간, 양도 허용, 양도 마감, 티켓당 양도 횟수, 승인제
- `claim(eventId, tier, voucher)` 관객 계정. 무료면 정원과 1인 최대만 검사. 유료(추후)는 결제 확인 서명 필수
- `_update` 오버라이드(모든 전송의 관문): 받는 쪽이 `Identity.isMember`인가, 받는 쪽의 이 공연 보유 수 < 1인 최대인가, 입장 전인가, 양도 마감 전인가, 양도 횟수 남았는가, 양도 허용 공연인가
- `checkIn(tokenId, G, S)` **게이트 계정만.** 7.2의 ①~⑤
- `requestOverride(tokenId, gateId, reason)` 매니저 · `manualOverride(tokenId, gateId, reason)` 승인 권한자
- `revoke(tokenId)`, `migrate(tokenId)`
- `tokenURI`: 체인 데이터로 JSON 조립 → `data:` URI. 이름, 설명, 이미지(IPFS CID), 속성(공연, 일시, 장소, 종류, 좌석, **상태: 입장 전/입장 완료**, 양도 가능)
- 이벤트 `EventCreated`, `Claimed`, `Transfer`, `CheckedIn(tokenId, eventId, gateId, nonceHash, ts)`, `OverrideRequested`, `ManualOverride(tokenId, gateId, approver, role, reason)`, `Revoked`, `Migrated`

**v2.7 추가(컨트랙트, 01c 승인제)**
- `Ticket`: 승인제 이벤트(`approvalRequired==true`)는 이제 온체인 신청→승인 경로로만 발급된다. `requestClaim(eventId, tier)` — 관객이 신청하고 `requestId`를 받는다(민팅 없음). `claim`과 같은 자격 검사(발행·판매창·멤버·KYC·티어·무료 전용)에 더해 **공급을 신청 시점에 예약**(`t.minted+=1`)해 승인이 초과 발행할 수 없고, **지갑당 한도를 대기+발급 합으로** 센다. `approveClaims(eventId, requestIds[])`/`rejectClaims(...)` — 소유자·`PERM_APPROVE_CLAIM`(비트 32) admin·`canApprove` 매니저. 승인은 `claim` 내부 경로로 민팅하고 `Claimed`도 함께 내보내 인덱서 `Ticket` 행이 정상 생성된다. 이미 대기가 아닌 요청은 배치를 되돌리지 않고 건너뛴다. `cancelRequest(eventId, requestId)` — 신청자 본인이 대기 요청을 취소(예약 해제). 이벤트 `ClaimRequested(eventId,requestId,requester,tier)`·`ClaimApproved(eventId,requestId,tokenId)`·`ClaimRejected(eventId,requestId)`(거절·취소 공용). 조회 `claimRequest(eventId,requestId)`·`pendingCount(eventId)`. 에러: `ApprovalRequiredNotSupported` **제거**, `ApprovalRequired`(승인제에서 직접 `claim`)·`ApprovalNotRequired`(선착순에서 `requestClaim`)·`RequestNotPending` 추가.
- `Paymaster`: 재배포 없이 배포 후 `setAllowed`로 셀렉터 4개 추가 — `requestClaim`·`approveClaims`·`rejectClaims`·`cancelRequest` 모두 `ArgKind.EventId` word 0(첫 인자 `eventId` 스칼라). 동적 배열이 뒤에 와도 첫 워드만 읽어 문제없다.
- **크기**: `Ticket` 런타임 26,351 → 29,574바이트(+3,223), Monad 한도 131,072 대비 여유 101,498바이트. `test/ContractSize.t.sol` 그대로 녹색.

**v2.6 추가(컨트랙트, 01b 번들 재배포 2026-10-05)**
- `Ticket`: `checkInLate(tokenId, G, S)` — 오프라인 큐 전용 입장 기록(12장). 게이트 계정만, 증명은 `checkIn`과 동일, 시계만 넓다(개장 −`LATE_WINDOW` ~ 폐장 +`LATE_WINDOW`, 12시간). 게이트가 열려 있을 필요는 없고 폐기된 게이트는 막힌다. 1회용 번호는 두 경로를 합쳐 **한 번만** 쓰인다. `CheckIn`에 `late` 추가, 이벤트 `CheckedInLate(tokenId, gateId, issuedAt, ts)`가 `CheckedIn`과 **함께** 나온다(입장 수를 셀 때는 `CheckedIn`만 센다). 되돌리는 사유 **12개는 `checkIn`과 완전히 같다** — 13장 DENY 코드는 움직이지 않는다.
- `Ticket`: 입장 기록 조회 `checkInOf(tokenId)`의 반환 구조가 `(gateId, nonceHash, ts, manual, late)`로 바뀌었다(셀렉터는 그대로라 컴파일러가 못 잡는다. 자리로 해체하는 코드는 전부 고쳐야 한다).

- `Ticket`: 양도 승인 서명이 **EIP-712**가 된다. `TransferApproval(uint256 tokenId,bytes32 recipientCommitment,address recipient)` / 도메인 `(MONTI Ticket, 1, chainId, verifyingContract)`. 조회 `offerDigest(tokenId, commitment, recipient)`, `eip712Domain()`. 같은 서명이 다른 체인·다른 배포본에서 더는 유효하지 않다.

"지금 되돌릴 수 있나"는 `rotatedFrom(personId) == 내 주소 && now < rotatedAt(personId) + 24시간`이다(`rotatedAt`은 `register`도 찍으므로 혼자서는 깃발이 아니다). `rotateAccount`가 옛 기기를 잠그고 `DeviceLocked`를 함께 내며, **되돌려도 그 잠금은 풀리지 않는다**(정상적인 `setActiveDevice` 경로로만 풀린다). `ROTATION_UNDO_WINDOW`는 `Ticket.MIGRATE_DELAY`와 같은 값이어야 한다.
- `Organizers`: `revokeGate`가 게이트 계정 매핑을 해제한다(폐기 뒤 재등록 가능, 페이마스터 스폰서 중단). `registerGate`가 반쪽 0 키를 거부한다.
- `Paymaster`: 허용 함수에 `checkInLate`, `cancelRotation`, `revokeGate`, `revoke`, `createOrganizer`, `transferOwner` 추가. **deployer 전용 `setAllowed(selector, kind, word)`** — 허용 목록 변경이 더는 재배포를 요구하지 않고, 남용되는 셀렉터를 한 트랜잭션으로 끌 수 있다(대상 컨트랙트 세 개는 그대로 불변 생성자 인자다). 조회 `argWordOf(selector)`, 이벤트 `SelectorAllowed`.

### 10.4 오프체인 저장소 운영 원칙 (창업자 확정)

**저장소는 Firebase 하나다. 프로덕션까지 쓴다.** 우리 DB는 장부가 아니라 개인정보 보관함이라 작다. Firestore는 대형 앱이 쓰는 검증된 운영 환경이고 서버 관리가 없다. 리전은 서울(asia-northeast3). 다른 DB로 옮기는 조건은 정해져 있다.

| 필요가 생기면 | 대응 |
|---|---|
| 매출·참석 통계 등 복잡한 분석 | DB 교체 없이 Firestore → BigQuery 자동 내보내기(공식 확장) |
| 여러 문서 동시 변경 트랜잭션, SQL 조인 | 그때 Postgres(Cloud SQL, Supabase, Neon)로 이전. 데이터가 작아 며칠 작업 |
| 같은 문서에 초당 수십 번 쓰기 | 우리 설계에 없음(그런 데이터는 체인과 인덱서) |

**개인정보는 절대 체인에 올리지 않고 우리가 암호화해서 갖는다.** 체인의 personId는 난수다. 이름·신분증 정보·사진은 Cloud KMS 키로 앱 단에서 한 번 더 암호화해 저장한다(Google 기본 암호화 위에 이중). DB가 통째로 유출돼도 KMS 키 없이는 읽을 수 없다. 복호화는 게이트 화면 표시와 스냅샷 발급 두 순간, 서버 함수 안에서만 일어난다.

**DB와 체인은 어긋날 수 없게 만든다.** 규칙 넷.

1. 체인에 있는 값은 우리 DB에 원본으로 두지 않는다. 티켓 상태, 권한, 입장 기록을 Firestore에 쓰지 않는다.
2. 우리 DB 문서의 열쇠는 체인 ID(personId, 계정 주소, tokenId)다. 반대 방향 참조는 없다.
3. 둘 다 건드리는 작업(가입, 계정 교체)은 "대기 → 체인 확정(`finalized`) → 완료(트랜잭션 해시·블록 번호 기록)" 순서. personId 기준 멱등. 주기적 대사 함수가 "대기"로 남은 항목을 체인과 비교해 고친다.
4. 캐시는 캐시라고 표시한다. 블록 번호를 붙이고, 이벤트로 갱신하고, 인덱서와 주기 대조해 틀리면 버린다.

**블록을 훑지 않는다. 인덱서가 스냅샷이다.** Monad `eth_getLogs`는 100블록(약 30초) 캡이라 직접 스캔은 불가능하다. Envio HyperIndex가 우리 컨트랙트 이벤트를 블록마다 실시간으로 정리하고, HyperSync로 처음부터 재구성할 수 있다. 여기에 **하루 한 번 인덱서 테이블을 Cloud Storage와 BigQuery로 내보내는 백업**을 둔다. 인덱서 장애 시 어제 데이터로 목록을 보여주며 재인덱싱하고, 통계와 감사 자료로 쓴다. 게이트 스냅샷(12장)은 별도의 공연별 오프라인 서명본이다.

## 12. 오프라인·장애 대응

| 상황 | 동작 | 이중 입장 위험 |
|---|---|---|
| 관객 폰 인터넷 없음 | **영향 없음.** 입장에 인터넷을 쓰지 않는다 | 없음 |
| 공연장 Wi-Fi 다운 | 단말기가 LTE 또는 핫스팟으로 계속. 관객 무관 | 없음 |
| 단말기 인터넷 없음 | **서명된 스냅샷** `{event, ticket, 계정, 기기 키, 사진, epoch, 만료} ‖ sig_attester`로 로컬 검증. "OFFLINE 승인"으로 표시하고 트랜잭션을 큐에 쌓아 복구 후 전송. 복구 후 보내는 것은 `checkIn`이 아니라 **`checkInLate(tokenId, G, S)`**다 — 현장 경로의 60초 창으로는 큐가 절대 들어갈 수 없기 때문이다. 큐 경로가 받는 코드는 **개장 12시간 전부터**이고, 제출은 **폐장 12시간 후까지** 가능하다(`LATE_WINDOW`). 나머지 증명은 현장과 똑같다: 큐의 트랜잭션은 관객 기기 키 서명이 있어야만 체인이 받고, 폐기된 게이트는 큐도 못 흘린다. 체인에 `CheckIn.late = true`와 `CheckedInLate` 이벤트가 남아 사후 대사가 가능하다 | **있음**(고립된 단말기끼리). 수용·기록·사후 대사. 두 번째 제출은 `AlreadyCheckedIn`으로 되돌아오고, 단말기는 체인의 `checkInOf`를 읽어 "누가 먼저였는지"를 기록한다 |
| 번들러 하나 다운 | 다음 번들러 | 없음 |
| NFC 안 되는 상황 | 폰이 같은 `{tokenId, S}`를 QR로 표시, 스태프 촬영. 이후 동일 | 없음 |

**차별점 보호**: turnstile에 없는 것이 이 표다.

## 15. 범위와 우선순위

### Must (없으면 제출 불가)

1. 웹앱 + Capacitor 껍데기(관객 iOS/Android, 스태프 Android)
2. 가입: 전화 인증 → 패스키 → 계정 배포·신원(등급 0)·기기 키 등록. 본인인증(Didit, 중복 검사)은 **행사별 토글**에 따라 필요할 때만, 등급 1로 승격
3. 주최자: 마법사로 프로젝트 생성(체인), 게이트 계정 등록·개폐, 매니저 초대(allowlist)
4. 관객: 티켓 받기(무료), 내 티켓
5. 입장: 무장 → NFC 읽기·쓰기 → 게이트 계정 체크인 → 스태프 화면 초록·빨강(체인 구독)
6. 양도: **닉네임·주소·전화번호 3경로**, 미가입자 문자 초대 + 전달 예약(offer), 사전 검사 알람, 온체인 규칙, 받은 티켓 인박스
7. 권한: 오너·관리자·매니저, 수동 승인·결재 요청
7a. **모바일 전용 UI**: 하단 탭 4개, 플로팅 버튼, 영어·한국어
7b. 탐색 필터(날짜·지역·테마), 행사 상태(초안·게시·취소), 닉네임·프로필
8. 페이마스터(우리 예산), 번들러, RPC 다중화
9. 4개 컨트랙트 테스트넷 배포, 공개 영수증 페이지(Envio)

### Should (차별점, 지킨다)

9a. **행사 대화방**(보유자 전용, 종료 시 닫힘, 순서 변경, 주최자 공지)
10. 단말기 오프라인: 스냅샷 로컬 검증 + 큐잉 + 복구 전송
11. NFC 불가 시 QR 폴백
12. 기기 잠금·7일 쿨타임 UI
13. 데모 영상, write-up, 카피 감사(크립토 단어 0)

### Could

14. 프로젝트별 가스 지갑 UI, 한국인 PortOne 빠른 경로, 좌석 지정, 참가 승인제 모임

### 제외 (해커톤 이후)

**유료 결제(PG)**, 재판매 시장·에스크로, 환불, 다일권·재입장, EAS, Guild, Apple/Google Wallet, 메인넷, 푸시 고도화.

## 부록 A. write-up용 문단 (영문 번역 예정)

회전 바코드 시스템은 관객에게 무기명 토큰을 쥐여준다. 화면에 뜬 것이 곧 티켓이고, 방어 전체가 "캡처가 낡기 전에 빨리 돌린다"에 걸려 있다. 우리는 그 구조를 뒤집었다. 관객은 Face ID로 티켓을 60초 동안 무장시키고, 게이트가 준 1회용 번호에 폰 보안 칩이 서명해 NFC로 돌려준다. 그 서명을 들고 체인에 쓰는 것은 관객도 우리 서버도 아니라 주최자가 체인에 등록한 게이트 단말기다. 컨트랙트가 게이트의 권한, 관객 기기의 서명, 시간 창, 티켓 상태를 한 번에 검사하고, 스태프 단말기는 결과를 체인에서 직접 읽는다. 관객 폰에는 훔칠 것도 인터넷도 필요 없고, 우리 서버에는 해킹할 가치가 있는 키가 없다. 모든 티켓의 발행, 양도, 입장, 수동 승인, 권한 변경이 Monad에 공개 기록으로 남는다. 주최자는 몰래 초과 판매할 수 없고 우리는 참석을 조작할 수 없으며, 누구든 우리와 계약 없이 그 기록 위에 규칙을 만들 수 있다. Monad의 0.3초 블록이 이 구조를 가능하게 했다. 체인이 회전문이 될 만큼 빠른 첫 체인이다.
